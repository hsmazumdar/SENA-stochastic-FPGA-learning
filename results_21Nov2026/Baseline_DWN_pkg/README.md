# DWN matched baseline for SENA (V13): run book

**Status: package only. It contains no baseline results.** Every accuracy, LE, Fmax and power number for the paper must come from *your* runs of the steps below. Files under `selftest/` are functional pipeline checks on tiny or random models and are **not** results.

**Paper wording, required.** DWN (Bacellar et al., ICML 2024) was retrained by us on SENA's split with the authors' code. The FPGA implementation is **our re-implementation** of the published DWN inference structure (LUT layers, then popcount, then argmax), generated by `dwn_to_verilog.py`, because the DWN authors did not release RTL.

## 1. Environment (Windows, any Windows PC)

**You may not need a GPU.** The package includes a pure-PyTorch implementation of DWN's LUT layer (`--efd torch`). It is a line-by-line transcription of the official CUDA kernel. On the build box (8 CPU cores) one epoch of the "sm" model took about 6 s on CPU, which is a timing measurement only. At that rate 100 epochs × 5 seeds is about 50 min on CPU, so it should run on the home i9-10900K too. The official CUDA extension (`--efd ext`) is the reference implementation; use it when a working NVIDIA GPU is available.

Open **cmd** in the package folder (`<SENA_ROOT>/Revision_V13\Baseline_DWN_pkg`) and run (needs Python 3.11 installed; `py -0` lists versions):

```bat
py -3.11 -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
```

**Option A: CPU only (no compile, works everywhere)**
```bat
pip install torch==2.7.1 --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
```

**Option B: NVIDIA GPU with the official DWN CUDA extension**
1. Run `nvidia-smi` and note the GPU model and driver version. The office card's exact model still needs confirming.
2. Install torch with CUDA. For most GPUs from GTX 10xx to RTX 40xx:
   `pip install torch==2.7.1 --index-url https://download.pytorch.org/whl/cu126`
   For an RTX 50xx, use `cu128` instead of `cu126`.
   Check it with `python -c "import torch;print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"`.
3. To build the extension you need **CUDA Toolkit 12.6** (or 12.8 to match cu128) and **Visual Studio 2022 Build Tools** with the "Desktop development with C++" workload. Open the **"x64 Native Tools Command Prompt for VS 2022"**, activate the venv, then run:
   ```bat
   pip install -r requirements.txt
   set DISTUTILS_USE_SDK=1
   pip install --no-build-isolation git+https://github.com/alanbacellar/DWN@2b456acfc7f679a8c8f6ea18835f47803aa5b0da
   python -c "import torch_dwn, efd_cuda; print('ext OK')"
   python train_dwn.py --check-efd
   ```
   `--check-efd` compares the official kernel with the fallback on random data and should print `True`.
4. **If the extension will not build on Windows** (a common problem: MSVC or CUDA version mismatch), keep the CUDA torch and train with `--efd torch`. That still runs on the GPU, just without the custom kernel. The `efd_backend` column in the CSV records which one you used, so say so in the paper.

**Option C: Google Colab T4.** Zip this whole folder as `Baseline_DWN.zip` (any folder name inside is fine), put it in your Drive root, open `DWN_Colab.ipynb` and run all cells.

Icarus Verilog (optional, for the RTL check on Windows): install from https://bleyer.org/icarus/ and tick "add to PATH".

## 3. Train 5 seeds
```bat
python train_dwn.py --arch sm --seeds 0 1 2 3 4 --efd ext      REM GPU + official extension
python train_dwn.py --arch sm --seeds 0 1 2 3 4 --efd torch    REM fallback (CPU or GPU)
```
- **Runtime estimate:** CPU fallback about 10 min per seed, extrapolated from a 1-epoch timing on the build box. The GPU is expected to be faster, but that hasn't been measured.
- Outputs go to `runs\sm\seed<k>\`: `model.json`, `test_scores.npz`, `epoch_log.csv` and `model_state.pt`. Each seed is also appended to `runs\sm\accuracy.csv`.
- A finished seed is never retrained or overwritten. Delete its folder if you deliberately want to rerun it.
- `int_vs_torch_agree` must read `2500/2500` for every seed. This confirms the exported LUT tables reproduce PyTorch exactly.
- Optional larger variant: `--arch lg_z1`, which uses the paper's "lg" sizes 2000/1000 and tau 1/0.173, with 1-bit input. This configuration is our own variant, not a published one.

### 3b. Already have Colab checkpoints from the earlier `baseline_dwn` attempt (13 Nov)?
The folder `<SENA_ROOT>/Revision_V13\baseline_dwn\` contains an earlier Colab training script, `train_sena_dwn_sm.py`. It uses the same "sm" config and the same split, and writes `checkpoints\dwn_sm_sena_seed<k>.pt`. If those checkpoints exist, convert them instead of retraining:

The converted runs go to `runs\sm_ckpt\`; use `--arch sm_ckpt` in steps 4 and 7. Report the final-epoch accuracy only. That script also logs `best_test_acc`, which is a best epoch chosen **on the test set** and must not be reported.

## 4. Generate Verilog for one seed and check it bit-exactly
Use **seed 0** for hardware, or the median-accuracy seed. Say which one you used.
```bat
python dwn_to_verilog.py runs\sm\seed0\model.json --out quartus\gen --sim
```
- `--sim` needs `iverilog`/`vvp` on PATH. Without them, omit `--sim` and run the same check later. It must print:
  `RESULT n=2500 pred_mismatch=0 count_mismatch=0 ... latency=5 expected_latency=5` followed by `BIT-EXACT PASS`.
  That means all 2,500 RTL predictions **and** all class popcounts equal the Python integer model.
- The generator refuses to write into a non-empty folder. For a second seed use, for example, `--out quartus\gen_seed1`, and copy it to `gen` only for the build.
- Pipeline: input register, LUT layer 1 register, LUT layer 2 register, popcount register, argmax register. That gives **latency = 5 clocks** and **one inference per clock**.

## 5. Quartus (DE2-115), about 5–15 min per revision
```bat
cd quartus
BUILD_DWN.bat            REM compile both revisions + timing + PowerPlay, copy reports
BUILD_DWN.bat program    REM same, then program the board (USB-Blaster)
```
or do it by hand: `quartus_sh -t compile_and_report.tcl de2_115_dwn` and `quartus_sh -t compile_and_report.tcl dwn_core_only`.

| Revision | Top | Purpose |
|---|---|---|
| `de2_115_dwn` | `de2_115_dwn_top` | On-board self-test at 25 MHz with the same pins, clock and LEDs as SENA. The 2,500 test vectors sit in an M9K ROM. Use the **`dwn_core:u_core`** row of "Fitter Resource Utilization by Entity" and of "Thermal Power Dissipation by Hierarchy" for the core-only numbers; the ROM and display belong to the test harness. |
| `dwn_core_only` | `dwn_core` | Core alone with virtual I/O and a 4 ns target, for clean LE, register and Fmax numbers. Don't use its I/O power. |

Reports are copied to `quartus\reports\<revision>\`. A time-stamped folder is used if that one already exists.

Notes for reading the reports:
- `dwn_core_only` **will** show `Critical Warning (332148): Timing requirements not met`. That is expected, because the 4 ns target is deliberately unreachable so the fitter pushes for speed. Read the achieved **Fmax** from the "Slow 1200mV 85C Model Fmax Summary". `de2_115_dwn` must meet timing at 25 MHz.
- Use **`dwn_core_only`** for LE and register counts. In the board build, Quartus can absorb the core's input register into the ROM's M9K output register, so the core's register count there is lower and not comparable.
- Cyclone IV logic elements are **4-input** LUTs, so each DWN LUT-6 node needs several LEs. DE2-115 LE counts are therefore **not** comparable with the DWN paper's Xilinx LUT-6 counts; the Artix-7 run gives LUT-6 numbers. Compare SENA and DWN on the same device only.

**On the board,** after programming:
- LEDG0 heartbeat.
- About 1 ms later, **LEDG[8:1] ON = PASS**: 0 mismatches against Python and a measured latency of 5. **LEDR17 = FAIL.**
- **KEY2** cycles the HEX display (the mode shows on LEDR[7:6]):
  - 00 = correct predictions out of 2500
  - 01 = RTL-vs-Python mismatches (must be 0000)
  - 10 = cycles from first input to last output (must be 2504 = 2500-1+5)
  - 11 = latency (0005)
- **KEY1** re-runs the test, **KEY0** resets.
- Photograph each mode for the supplement.

## 7. Tabulate
```bat
python collect_results.py --arch sm --board-mhz 25
```
It writes these files to `results\`:
- `dwn_accuracy_summary.csv`: mean ± sd over the seeds (sample sd)
- `dwn_coverage.csv`: accuracy at 100/90/80/70 % coverage, ranked by the GroupSum margin (top-1 minus top-2 popcount). This is the "free confidence" comparison for SENA's selective prediction.
- `dwn_hardware.csv`: every parsed Quartus or Vivado report
- `dwn_paper_table.csv`: the Table IIb row

**Numbers to record for the paper (Table IIb, "measured in this work"):**
1. Accuracy, mean ± sd over 5 seeds, on the 2,500-image test set, plus the backend used (ext or torch) and the GPU or CPU name.
2. Accuracy at 90%, 80% and 70% coverage.
3. DE2-115:
   - LE (total, and `dwn_core:u_core`), registers, memory bits (core should be 0) and 9-bit multipliers (should be 0)
   - Fmax, Slow 1200mV 85C, from `dwn_core_only`
   - latency = 5 cycles, which is 200 ns at 25 MHz and 5/Fmax at Fmax
   - throughput = 1 inference per clock (25 M inferences/s at 25 MHz)
   - PowerPlay core dynamic power of `dwn_core:u_core` at 25 MHz, and energy per inference = P_dyn / 25 MHz (streaming) or × 5 cycles (single shot), labelled "post-fit vectorless estimate", the same tier as SENA's Table XIII
   - the board self-test result (PASS, correct count)
4. Optionally, for Artix-7: LUT, FF, BRAM and DSP, Fmax from WNS, and Vivado power.
5. Which seed was built in hardware (`model_sha256` in `quartus\gen\dwn_core_info.json`).
